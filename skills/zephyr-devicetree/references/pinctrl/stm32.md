# STM32 pinctrl

When to read this: you are assigning, moving, or debugging pins on an STM32 target
(boards like `nucleo_*`, `disco_*`). Read `references/pinctrl/model.md` first for the
vendor-independent model; this page covers only what STM32 does differently.

## Identification

- SoC qualifier prefix: `stm32`. On Zephyr 4.0 or newer, read the first `/`-segment of
  `cmake.board.qualifiers` in `build/build_info.yml` (for example `stm32f407xx`).
- Board name patterns (pre-build fallback): `nucleo_*`, `disco_*`, `stm32*`.

## Where pin data lives

Pin data ships as devicetree source, not C headers. ST's HAL module carries one
autogenerated (by `genpinctrl.py`, stable format) dtsi per chip:

```
modules/hal/stm32/dts/st/<series>/<chip>-pinctrl.dtsi
```

The chip stem matches the silkscreen part number, so the board name usually tells you
the file: `nucleo_h563zi` uses `modules/hal/stm32/dts/st/h5/stm32h563zitx-pinctrl.dtsi`.
Locate it directly:

```shell
find <west-topdir>/modules/hal/stm32/dts/st -name 'stm32h563*-pinctrl.dtsi'
```

The `modules/hal/stm32` tail can sit at different depths depending on the west
manifest; with a build on Zephyr 4.0 or newer, `cmake.devicetree.include-dirs` in
`build/build_info.yml` lists every HAL DTS root CMake used, so consult it instead of
guessing (see `references/build-artifacts.md`).

The `STM32_PINMUX` macro itself is defined in
`$ZEPHYR_BASE/include/zephyr/dt-bindings/pinctrl/stm32-pinctrl.h`
(F1 parts use `stm32f1-pinctrl.h`, a different scheme: see Out of scope).

## Authoring format and macro

Style: direct-ref. The chip dtsi ships one labelled node per (pad, signal) pair, and
your overlay references those labels from `pinctrl-N`. You normally never write
`STM32_PINMUX` yourself; you pick existing labels.

Node naming convention: `<peripheral>_<role>_p<port><pin>`, ports `a` to `k`, pins
0 to 15. Examples: `usart1_tx_pa9`, `i2c1_scl_pb8`, `tim1_ch1_pa8`. List what a
peripheral offers on your chip:

```shell
grep -n 'usart1_' <west-topdir>/modules/hal/stm32/dts/st/h5/stm32h563zitx-pinctrl.dtsi
```

Each shipped node looks like this:

```dts
/omit-if-no-ref/ usart1_tx_pa9: usart1_tx_pa9 {
    pinmux = <STM32_PINMUX('A', 9, AF7)>;
};
```

Gap-fill: `/omit-if-no-ref/` tells the compiler to drop the node from the final DT
unless something references it, so only the signals you actually use appear in
`build/zephyr/zephyr.dts`.

`STM32_PINMUX(port, line, mode)` packs one 32-bit cell:

```c
/* $ZEPHYR_BASE/include/zephyr/dt-bindings/pinctrl/stm32-pinctrl.h */
/* bits 0-4  MODE: AF0..AF15 = 0..15, ANALOG = 0x10, GPIO = 0x11   */
/* bits 5-8  LINE: pin number 0..15                                */
/* bits 9-13 PORT: 'A' = 0, 'B' = 1, ...                           */

/* STM32_PINMUX('A', 9, AF7) = (0 << 9) | (9 << 5) | 7 = 0x127 */
```

Because the overlay references labels (phandles), the labels survive into
`build/zephyr/zephyr.dts`: grep for the label name to verify a routing, no numeric
decoding needed (the signal node's body will show the packed value, `pinmux = < 0x127 >`).

## Node shape example

Worked example: enable USART1 on `nucleo_h563zi` with TX on PA9 and RX on PA10.

1. Confirm the labels exist in the chip dtsi:

```shell
grep -nE 'usart1_(tx|rx)_' <west-topdir>/modules/hal/stm32/dts/st/h5/stm32h563zitx-pinctrl.dtsi
```

2. Write the board overlay (`<app>/boards/nucleo_h563zi.overlay`; see
   `references/overlay-authoring.md` for placement rules):

```dts
&usart1 {
    pinctrl-0 = <&usart1_tx_pa9 &usart1_rx_pa10>;
    pinctrl-names = "default";
    current-speed = <115200>;
    status = "okay";
};
```

   Gap-fill: `current-speed` is the standard baud property from the UART controller
   binding; check the binding in your checkout for whether it is required on your part.

3. Enable the driver in `prj.conf` (devicetree alone enables nothing).
   Gap-fill: the serial subsystem toggle is `CONFIG_SERIAL=y`; verify the exact symbol
   against your checkout.

4. Rebuild and verify in the resolved tree:

```shell
west build
grep -n -A 6 'usart1' build/zephyr/zephyr.dts
```

   Expect `status = "okay"` and `pinctrl-0 = < &usart1_tx_pa9 &usart1_rx_pa10 >` on
   the node.

Moving pins is the same edit with different labels: grep the chip dtsi for the
alternates it offers and swap them in `pinctrl-0`. Gap-fill: on many parts USART1
also routes to PB6/PB7 (`usart1_tx_pb6`, `usart1_rx_pb7`); trust the grep output for
your chip, not this list.

## Required includes

None for the normal case. STM32 `pinctrl-N` cells are phandle references to labels
that already exist in the merged tree, so the overlay needs no `#include`.

Only if you define a brand-new pinmux node carrying the macro yourself (rare; the
generated dtsi is nearly exhaustive) does the overlay need the macro header:

```dts
#include <zephyr/dt-bindings/pinctrl/stm32-pinctrl.h>

&pinctrl {
    my_custom_pa9: my_custom_pa9 {
        pinmux = <STM32_PINMUX('A', 9, AF7)>;
    };
};
```

## Defaults and per-peripheral conventions

- Write `pinctrl-0` as one phandle group: `<&usart1_tx_pa9 &usart1_rx_pa10>`, and
  always pair it with `pinctrl-names` (positional; slot 0 is `"default"`).
- Electrical properties (bias, drive, slew) mostly ship on the generated signal
  nodes; some entries already carry extra slew or bias settings. Gap-fill: to tweak
  one signal, re-open its label in your overlay and add standard pinctrl properties
  (`bias-pull-up;`, `drive-open-drain;`, ...); verify the accepted property set
  against the pinctrl binding in your checkout.
- Pin-set completeness rules, in STM32 spelling (see `references/pinctrl/model.md`
  for the cross-vendor table):

| Family (STM32 label prefixes) | Required pins |
| --- | --- |
| `i2c` | SCL and SDA, always as a pair |
| `uart`, `usart`, `lpuart` | TX always; RX required unless `single-wire` and forbidden with it; `hw-flow-control` additionally requires CTS and RTS |
| `can`, `fdcan` | TX and RX, both |
| `spi` | SCK required iff MOSI or MISO is present (SCK alone is legal) |

  `single-wire` comes from the `st,stm32-uart-base` binding; `hw-flow-control` from
  the generic UART controller binding.
- ADC channels follow the cross-vendor Zephyr convention: children of the ADC node
  named `channel@<reg>`.

## Quirks

- Timer PWM pins: the pinctrl signal is named `tim<N>_ch<M>_p<port><pin>` but the DT
  node is labelled `timers<N>`, and `pinctrl-N` does not go on that wrapper: it goes
  on the wrapper's `pwm` child. The child is a compatible-bearing sub-device
  (`st,stm32-pwm` under `st,stm32-timers`) with its own binding and driver, so enable
  both:

```dts
&timers1 {
    status = "okay";

    pwm1: pwm {
        pinctrl-0 = <&tim1_ch1_pa8>;
        pinctrl-names = "default";
        status = "okay";
    };
};
```

- `st,stm32-lptim` does not declare `pinctrl-N` in some Zephyr versions: the driver
  does not read pinctrl there, so adding `pinctrl-0` to it does nothing. Check the
  binding in your checkout before assuming a peripheral takes pinctrl.
- Binding-valid is not boot-valid on the STM32 ADC: `adc_stm32_channel_setup` in
  `$ZEPHYR_BASE/drivers/adc/adc_stm32.c` rejects, at boot with `-EINVAL`, channel
  children of `st,stm32-adc` that set `differential`, any `zephyr,gain` other than
  `ADC_GAIN_1`, or any `zephyr,reference` other than `ADC_REF_INTERNAL`, even though
  the binding accepts them (see `references/validation-rules.md`).
- Derivative compatibles like `st,stm32f4-adc` resolve through the base
  `st,stm32-adc.yaml` binding; match on both when searching bindings.
- Drift check: overlays and `zephyr.dts` both show labels on STM32, so a plain grep
  comparison works here (unlike macro-cell vendors, where you must compare resolved
  integers; see `references/debugging.md`).

## Out of scope

- STM32F1 numeric decode: F1 parts use a remap-based scheme with their own constants
  in `stm32f1-pinctrl.h`, and the packed `pinmux` values differ entirely from the
  layout above. Authoring by referencing the labels in the F1 chip dtsi still works
  exactly as shown here; decoding raw F1 `pinmux` integers found in `zephyr.dts` is
  not covered.
