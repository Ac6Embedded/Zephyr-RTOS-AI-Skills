# ESP32 pinctrl (Espressif)

When to read this: you are assigning, moving, or reviewing pins on an Espressif ESP32-family
SoC (esp32, esp32s2, esp32s3, esp32c2, esp32c3, esp32c5, esp32c6, esp32h2). Read
references/pinctrl/model.md first for the vendor-independent model; this page adds the ESP32 specifics.

## Identification

- SoC qualifier: the first `/` segment of `cmake.board.qualifiers` in `build/build_info.yml`
  (Zephyr 4.0 or newer) starts with `esp32`. Example: `esp32s3_devkitc/esp32s3/procpu` gives
  variant `esp32s3`.
- Board name patterns: `esp32*` (`esp32_devkitc`, `esp32s3_devkitc`, ...) plus dev kits whose
  public names drop the `esp32` substring: Seeed `xiao_*`, `m5stack_*`, `heltec_*`.
- Match the longest variant token first when deriving the variant from a board identifier:
  `esp32s3_devkitc` contains both `esp32s3` and `esp32`, and the variant is `esp32s3`. Picking
  the bare `esp32` headers for an S3 board yields wrong signal indexes.

## Where pin data lives

ESP32 pin data lives in the Zephyr repository itself, not under `modules/hal/espressif`. Each
variant ships a paired set of headers (autogenerated upstream):

| File | Content |
| --- | --- |
| `$ZEPHYR_BASE/include/zephyr/dt-bindings/pinctrl/<variant>-pinctrl.h` | thousands of packed pinmux defines, one per (peripheral signal, GPIO) pair |
| `$ZEPHYR_BASE/include/zephyr/dt-bindings/pinctrl/<variant>-gpio-sigmap.h` | signal index constants such as `#define ESP_U0RXD_IN 12` |
| `$ZEPHYR_BASE/include/zephyr/dt-bindings/pinctrl/esp-pinctrl-common.h` | the shared `ESP32_PINMUX` packing macro and `ESP_SIG_INVAL` |

Variants: `esp32`, `esp32c2`, `esp32c3`, `esp32c5`, `esp32c6`, `esp32h2`, `esp32s2`, `esp32s3`.
Signal indexes are variant specific (a UART signal index on ESP32-S3 is not the same number on
ESP32-C3), so the pinctrl header and the sigmap must come from the same variant.

The board's shipped assignments live in the board pinctrl shell dtsi,
`$ZEPHYR_BASE/boards/<vendor>/<board>/<board>-pinctrl.dtsi`. Gap-fill: for Espressif dev kits
the vendor segment is `espressif` (for example
`boards/espressif/esp32s3_devkitc/esp32s3_devkitc-pinctrl.dtsi`); dev kits from other makers
sit under their maker's directory. Verified against upstream main; double-check the exact path
in your checkout. Imitate the shipped file when in doubt.

List the candidate symbols for a peripheral before writing an overlay:

```shell
grep "SPIM3_.*_GPIO" "$ZEPHYR_BASE/include/zephyr/dt-bindings/pinctrl/esp32s3-pinctrl.h" | head -20
```

## Authoring format and macro

Silicon model: a flat GPIO matrix. There are no port banks; every pad is named `GPIO<N>`, and
nearly any peripheral signal can be routed to nearly any pin. The ESP32-S3 header alone holds
about 7400 defines (49 GPIOs times roughly 150 peripheral roles) because the matrix really does
allow almost every permutation.

Authoring style: group (one of the three styles in references/pinctrl/model.md). The peripheral
node's `pinctrl-0` points at a group node under `&pinctrl`; the group node's `groupN` children
carry the `pinmux` cell lists.

Symbol shape is `<PERIPHERAL>_<SIGNAL>_GPIO<N>`:

```c
/* <variant>-pinctrl.h line shape (signal indexes vary per variant) */
#define UART0_TX_GPIO18   ESP32_PINMUX(18, ESP_NOSIG, ESP_U0TXD_OUT)
#define SPIM3_MISO_GPIO13 ESP32_PINMUX(13, ESP_SPI3_Q_IN, ESP_NOSIG)
```

`ESP32_PINMUX(pin, sig_in, sig_out)` packs each cell into a single integer (24 bits used):

```c
value = (pin & 0x3F) | ((sig_in & 0x1FF) << 6) | ((sig_out & 0x1FF) << 15);
```

`ESP_SIG_INVAL` (0x1FF) marks a direction the signal does not use; `ESP_NOSIG` is an alias for
it, defined in `esp-pinctrl-common.h`, not in the sigmap.

Two formatting rules (details in references/pinctrl/model.md):

- The macro is a cell value, never a phandle: write `pinmux = <SPIM3_MOSI_GPIO11>;` and never
  `pinmux = <&SPIM3_MOSI_GPIO11>;`.
- Multiple cells keep their commas: `pinmux = <A>, <B>;` must not collapse to `<A B>`.

After a build, only the packed integers remain in `build/zephyr/zephyr.dts`. Grep for the group
node name, not the macro symbol (see references/build-artifacts.md):

```shell
grep -A 12 "pinmux_spi3_default" build/zephyr/zephyr.dts
```

## Node shape example

Worked example: route SPI3 on an ESP32-S3 board with the split-group layout ESP32 uses. Put
this in the app's board overlay (file placement rules: references/overlay-authoring.md).

```dts
#include <zephyr/dt-bindings/pinctrl/esp32s3-pinctrl.h>

&pinctrl {
    pinmux_spi3_default: pinmux_spi3_default {
        group1 {
            /* Input and clocked signals: no extra electrical flags */
            pinmux = <SPIM3_MISO_GPIO13>,
                     <SPIM3_SCLK_GPIO12>,
                     <SPIM3_CSEL_GPIO10>;
        };
        group2 {
            /* MOSI idles low between transfers */
            pinmux = <SPIM3_MOSI_GPIO11>;
            output-low;
        };
    };
};

&spi3 {
    status = "okay";
    pinctrl-0 = <&pinmux_spi3_default>;
    pinctrl-names = "default";
};
```

Notes:

- The `group1`/`group2` split exists so MOSI can carry `output-low` while the other signals
  carry no flags. Do not merge the groups to shorten the file: group properties apply to every
  cell in the group.
- The pins here are illustrative. The GPIO matrix accepts nearly any free pin; confirm each
  symbol exists in your variant's header with the grep shown earlier, and check the board
  schematic for pins already committed elsewhere.
- `pinctrl-names` is positional and slot 0 is `"default"`; never write `pinctrl-0` without it.
- Devicetree routing alone does not enable the bus: set `CONFIG_SPI=y` in `prj.conf`. Putting
  devices on the bus (`reg`, `spi-max-frequency`, `cs-gpios`) is covered in
  references/buses-and-devices.md.

Build and confirm the resolved result:

```shell
west build -b esp32s3_devkitc/esp32s3/procpu <app-dir>
grep -A 12 "pinmux_spi3_default" build/zephyr/zephyr.dts
```

## Required includes

Every overlay that uses pinmux macros needs the variant pinctrl header, above all node blocks:

```dts
#include <zephyr/dt-bindings/pinctrl/esp32s3-pinctrl.h>
```

- One include is enough. Gap-fill: the `-pinctrl.h` header itself includes the matching
  `-gpio-sigmap.h` and `esp-pinctrl-common.h` (verified on upstream main; worth a quick look
  in older checkouts).
- Match `<variant>` to the SoC actually being built. A wrong-variant header can resolve
  same-named symbols to wrong signal indexes and silently mis-route pins.
- There is no include-free path on ESP32: every assignment uses macros (STM32-style direct
  label references do not exist here).
- If the `#include` fails to resolve, confirm the directory appears in
  `cmake.devicetree.include-dirs` of `build/build_info.yml` (Zephyr 4.0 or newer); see
  references/build-artifacts.md. Insertion and dedup rules when merging into an existing
  overlay: references/overlay-authoring.md.

## Defaults and per-peripheral conventions

- Group node label: `pinmux_<peripheral>_default` is a safe convention. Gap-fill: shipped board
  files use the shorter `<peripheral>_default` form (`uart0_default`, `spim3_default`; verified
  on upstream main). Any label works: the peripheral references the group by `&label`.
- Group children are conventionally named starting at `group1`.
- ESP32 splits configuration across multiple groups per peripheral so different signals can
  carry different electrical properties:

| Peripheral | Conventional layout |
| --- | --- |
| UART | `group1 { pinmux = <TX>; output-high; };` plus `group2 { pinmux = <RX>; bias-pull-up; };` |
| I2C | one group: `group1 { pinmux = <SDA>, <SCL>; bias-pull-up; drive-open-drain; output-high; };` |
| SPI master | `group1 { pinmux = <MISO>, <SCLK>, <CSEL>; };` plus `group2 { pinmux = <MOSI>; output-low; };` |

- Pin-set requirements (family rules, full table in references/pinctrl/model.md): I2C needs SCL
  and SDA as a pair; UART needs TX, and RX unless configured single-wire; SPI needs SCLK
  whenever MOSI or MISO is present (SCLK alone is legal, clock-only); CAN needs TX and RX.

## Quirks

- The SPI clock signal is `SCLK`, not `SCK`: symbols are `SPIM<N>_SCLK_GPIO<M>`. Requirement
  checks on ESP32 key on `SCLK`.
- SPI naming mismatch: the DT node label is `spi3` (compatible `espressif,esp32-spi`) but the
  header symbols carry the `SPIM3` prefix (SPI master).
- CAN is called `twai` on ESP32: the node label is `&twai` and the symbols are
  `TWAI_TX_GPIO<N>` and `TWAI_RX_GPIO<N>`.
- The pinctrl parent's node path is `/pin-controller`, not `/pinctrl`; its DT label is still
  `pinctrl`. Always write `&pinctrl { ... };`, never address it by path.
- The legacy `esp32` variant's sigmap omits `ESP_U1DSR_IN` and `ESP_U1DTR_OUT`, so the UART1
  DSR/DTR pinmux defines that reference them do not compile. Avoid those two signals on the
  original ESP32.
- Reverse lookup is numeric: an existing assignment shows in `zephyr.dts` as
  `pinmux = < 0x... >`. To identify it, unpack with the bit layout above (pin is
  `value & 0x3F`) and match the signal indexes against the variant's sigmap.

## Out of scope

- All listed variants share the single `ESP32_PINMUX` encoding; there is no second ESP32
  encoding family to watch for (no analog of the STM32 F1 remap scheme or Silabs Series 1).
- Variants outside the list above (newer chips such as `esp32p4`): check your checkout for a
  `<variant>-pinctrl.h` plus `<variant>-gpio-sigmap.h` pair under
  `$ZEPHYR_BASE/include/zephyr/dt-bindings/pinctrl/`; if the pair exists, this page applies
  unchanged.
- Gap-fill: board-level pin reservations are real on ESP32 modules (strapping pins, pads wired
  to the on-module SPI flash or PSRAM) and are not modeled by devicetree, so the build cannot
  catch them; upstream board files carry comments such as SPI3 pins reserved for octal PSRAM on
  some S3 kits. Check the SoC datasheet and the board schematic before committing a pin.
- Runtime pinctrl state switching from C is not covered by this skill.
